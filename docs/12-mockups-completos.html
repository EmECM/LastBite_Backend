Categorías con ícono y color

Decisión tomada: el ícono y el color viven en la aplicación, no en la base de datos. Este mapa es la única fuente de verdad y debe replicarse tal cual en Flutter, asociando cada categoría por su nombre.

Por qué en la app y no en la base. El ícono depende del set gráfico de Flutter y el color es una decisión de marca, no un dato del negocio. Guardarlos en la base obligaría a una migración cada vez que se ajusta un tono. El costo de esta decisión es que agregar una categoría nueva exige recompilar la aplicación, y como las seis categorías vienen de los datos semilla y no cambian, ese costo es cero en la práctica.

Regla para el desarrollo: si llega una categoría que no está en el mapa, se usa un ícono y un color neutro por defecto. Nunca debe romperse la pantalla por eso.

01 · Cómo se escribe

Convenciones de código

Cada pantalla de este documento lleva un bloque de contrato técnico con su endpoint, las clases de C# que lo atienden y el servicio de Flutter que lo consume. Esta sección explica las reglas que siguen todos esos nombres.

La cadena completa, de la pantalla a la base

Pantalla→ Controlador→ Api (interfaz)→ HTTP + JSON→ Controller→ IService→ IRepository→ Dapper→ Procedimiento o vista

Ninguna capa se salta. La pantalla no llama HTTP directamente y el controlador de C# no consulta la base: entre ambos siempre hay una interfaz, que es lo que permite trabajar con respuestas simuladas mientras la otra parte no está lista.

Backend · C# y .NET

Estructura de carpetas

  • Controllers/ — un archivo por recurso
  • Services/ — interfaz y su implementación
  • Repositories/ — todo el SQL vive aquí
  • Dtos/ — objetos de entrada y salida
  • Common/ — conexión, errores, token

Nombres

  • Controlador en plural: ReservasController
  • Servicio en singular con interfaz: IReservaService y ReservaService
  • Repositorio igual: IReservaRepository
  • Entrada: sufijo Request. Salida: sufijo Response
  • Métodos asíncronos terminan en Async
  • Clases y métodos en PascalCase; parámetros en camelCase

Reglas

  • El controlador no tiene lógica: valida, llama al servicio y devuelve
  • Los DTO nunca son la entidad de la base; se mapean explícitamente
  • Todo el SQL está en el repositorio, nunca en el controlador
  • Un solo middleware traduce los errores del procedimiento a HTTP
  • Cada petición fija app.usuario_id al abrir la conexión

Frontend · Flutter y Dart

Estructura de carpetas

  • lib/api/ — interfaces e implementaciones HTTP
  • lib/modelos/ — clases con fromJson
  • lib/estado/ — controladores de pantalla
  • lib/pantallas/ — una por vista
  • lib/widgets/ — piezas reutilizables
  • lib/nucleo/ — cliente HTTP, errores, formatos

Nombres

  • Archivos en snake_case: reserva_api.dart
  • Clases en PascalCase: ReservaApiHttp
  • La interfaz es una abstract class con sufijo Api
  • La implementación agrega Http: ReservaApiHttp
  • El estado lleva sufijo Controlador
  • Las pantallas llevan prefijo Pantalla

Reglas

  • La pantalla no llama a la API: habla con su controlador
  • Todo modelo tiene fromJson; los de entrada, toJson
  • Un solo ClienteApi agrega el token y traduce los errores
  • La app nunca calcula dinero: muestra el total que devuelve el backend
  • Los estados llegan como texto en mayúsculas y se traducen para mostrar

El JSON que viaja entre los dos

  • Claves en camelCase, tanto de ida como de vuelta.
  • Fechas en formato ISO 8601. Las horas de retiro viajan como texto "18:00" porque son horas de pared, no instantes.
  • Los importes viajan como número con dos decimales. En C# son decimal; en Dart se leen como num y solo se formatean para mostrar.
  • Todo error tiene la misma forma: { "codigo": "SIN_CUPO", "mensaje": "..." }. El codigo es estable y es el que la app usa para decidir qué texto mostrar.

Ejemplo completo: reservar una bolsa

Es el recorrido más representativo porque atraviesa las nueve capas y termina en un procedimiento almacenado con parámetros de salida.

// ---------- Flutter · lib/api/reserva_api.dart
abstract class ReservaApi {
  Future<ReservaCreada> crear(CrearReservaPeticion p);
}

class ReservaApiHttp implements ReservaApi {
  final ClienteApi cliente;
  ReservaApiHttp(this.cliente);

  @override
  Future<ReservaCreada> crear(CrearReservaPeticion p) async {
    final json = await cliente.post('/api/reservas', p.toJson());
    return ReservaCreada.fromJson(json);
  }
}

// ---------- lib/estado/reserva_controlador.dart
class ReservaControlador extends ChangeNotifier {
  final ReservaApi api;
  EstadoCarga estado = EstadoCarga.inicial;
  String? mensajeError;

  Future<void> reservar(int publicacionId, int cantidad, int metodoPagoId) async {
    estado = EstadoCarga.cargando; notifyListeners();
    try {
      final r = await api.crear(CrearReservaPeticion(
        publicacionId: publicacionId, cantidad: cantidad, metodoPagoId: metodoPagoId));
      estado = EstadoCarga.listo; reserva = r;
    } on ApiExcepcion catch (e) {
      mensajeError = mensajesError[e.codigo] ?? 'No se pudo completar la reserva.';
      estado = EstadoCarga.error;
    }
    notifyListeners();
  }
}

El detalle que más tiempo puede costar. En PostgreSQL, llamar a un procedimiento con parámetros de salida exige pasar marcadores para esos parámetros y la llamada devuelve una fila con los valores. Si se omiten, el motor responde procedure does not exist. Por eso el repositorio usa QuerySingleAsync y no ExecuteAsync. Está verificado sobre PostgreSQL 16.
